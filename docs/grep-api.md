# API grep для MVP

В рамках этой задачи определяется только контракт
Реализация поиска на C++ и cgo-обвязка на Go будут отдельной работой
Планируемая функция обвязки имеет следующую сигнатуру

```go
func Grep(paths []string, patterns []string, options GrepOptions) (GrepResult, error)
```

Go-типы и соответствующий тип функции `GrepFunc` находятся в `src/cppengine/grep_types.go`
До готовности обвязки код CLI может принимать `GrepFunc` и использовать тестовую реализацию
Объявления на C находятся в `src/cppengine/lq_grep.h`
Go-контракт использует существующий тип `FileStatus` из обвязки overview в пакете `cppengine`

## Входные данные и правила поиска

| Параметр | Контракт |
|---|---|
| `paths` | Уже найденные пути к обычным файлам в порядке вызывающего кода |
| `patterns` | Непустой список буквальных байтовых строк для поиска подстрок с учётом регистра и объединением через ИЛИ |
| `Workers` | Минимум 1 — последовательную или параллельную обработку выбирает C++ |
| `CountOnly` | Полный подсчёт совпавших строк без сохранения их текста |
| `MaxMatches` | Положительный лимит в обычном режиме — при `CountOnly=true` игнорируется и может быть равен 0 |

Go разбирает аргументы CLI и отвечает за обход каталогов и распаковку архивов
Движок сам открывает подготовленные пути и не получает от Go полное содержимое файлов
Go отклоняет NUL внутри пути — в C ABI пути должны завершаться нулевым байтом
Шаблоны и возвращаемый текст имеют явную длину в байтах и могут содержать NUL
Пустой шаблон разрешён и совпадает с каждой существующей строкой включая пустую
LF внутри шаблона недопустим — многострочный поиск не входит в MVP
Поиск по UTF-8 выполняется как по байтам без преобразования регистра и нормализации Unicode

Параметры и шаблоны проверяются даже при пустом списке путей
Пустой список путей с корректными остальными аргументами возвращает пустой результат без ошибки
Файлы должны оставаться неизменными до возврата из вызова — реализация может читать диапазоны повторно
MVP не создаёт снимок файлов при одновременной записи в них

## Результаты

В `Files` находится одна запись на каждый входной путь — `Files[i]` соответствует `paths[i]`
`Lines` считает физические строки
`MatchingLines` учитывает каждую подходящую строку один раз независимо от числа сработавших шаблонов и вхождений
В пустом файле нет строк — непустая последняя строка без LF учитывается
Завершающий LF не создаёт дополнительную строку в конце файла

`Matches` упорядочен сначала по `FileIndex` и затем по `LineNumber`
`FileIndex` начинается с 0 — `LineNumber` начинается с 1
`Text` содержит исходную строку без завершающего LF
CR из CRLF сохраняется — текст не обязан завершаться NUL
Одинаковые шаблоны не приводят к дублированию совпавших строк
Повторяющиеся входные пути обрабатываются как отдельные записи с собственными индексами файлов

`MaxMatches` ограничивает число возвращаемых строк по всему запросу в том же порядке
Все файлы по-прежнему сканируются полностью и их счётчики остаются полными
`Truncated` равен `true` только при пропуске части совпавших строк из-за лимита
Если число совпавших строк точно равно лимиту — ничего не пропущено и `Truncated=false`

В режиме подсчёта `Matches` пустой и `Truncated=false`
Флаг `-n` относится к форматированию на Go — движок всегда возвращает номера строк
Флаг `-c` преобразуется в `CountOnly=true`

## Ошибки

Используются существующий Go-тип `FileStatus` и общие C-перечисления `lq_file_status` и `lq_call_status`

| Ситуация | Результат |
|---|---|
| Файл не удалось открыть или прочитать | Статус файла отличается от OK — все его счётчики равны нулю и совпадения из этого файла отсутствуют |
| Ошибка диапазона внутри файла | Результат всего файла сбрасывается по тому же правилу — остальные файлы продолжают обрабатываться |
| Ошибки одного или нескольких файлов | Сам вызов завершается успешно — Go `error` равен `nil` |
| Некорректный запрос или внутренняя ошибка всего вызова | Статус вызова отличается от OK и нативный результат пустой — Go возвращает ненулевой `error` |

Ошибкой вызова считаются нулевое число потоков и пустой список шаблонов
К ошибкам вызова также относятся LF внутри шаблона и нулевой лимит текста в обычном режиме
Исключения C++ не должны выходить через обе функции C ABI

## C ABI и владение памятью

```c
int32_t lq_grep(const lq_grep_request* request, lq_grep_result* result);
void lq_grep_free(lq_grep_result* result);
```

| C-тип | Назначение |
|---|---|
| `lq_pattern` | Данные шаблона и длина в байтах |
| `lq_grep_request` | Пути и шаблоны вместе с числом потоков и параметрами сбора текста |
| `lq_grep_file_stats` | Число всех строк и совпавших строк вместе со статусом файла |
| `lq_grep_match` | Индекс файла и номер строки вместе с указателем на текст и длиной в байтах |
| `lq_grep_result` | Массивы результатов только для чтения с их размерами и флагом усечения — владение хранится в служебном указателе |

`request` и `result` не должны быть нулевыми указателями
При положительном `file_count` указатель `paths` и каждый указатель на путь должны быть ненулевыми
`pattern_count` должен быть положительным — указатель `patterns` должен быть ненулевым
Указатель на данные шаблона должен быть ненулевым при положительной длине
`count_only` принимает только 0 или 1 — `truncated` возвращает только 0 или 1
При успешном вызове размеры массивов соответствуют длинам Go-срезов
Для массивов нулевого размера допускаются нулевые указатели

Будущая Go-обвязка выполняет следующие шаги

1. Проверяет Go-аргументы и выделяет запрос вместе с массивами путей и шаблонов в C-памяти
2. Инициализирует нулями нативный результат и синхронно вызывает `lq_grep`
3. Копирует массивы и текст успешного результата в Go-значения с учётом явных длин
4. Освобождает нативный результат через `lq_grep_free` и освобождает входные C-буферы

Входные буферы остаются во владении Go — C++ использует их только во время вызова
Память результата принадлежит C++ до вызова `lq_grep_free` — Go должен скопировать данные до освобождения
`internal` является служебным указателем
Вызывающий код не должен разбирать его содержимое или копировать владеющую структуру результата
Отдельные поля результата нельзя освобождать через `C.free`
`lq_grep_free` принимает нулевой указатель или инициализированный нулями результат и обнуляет все поля после освобождения
Функция вызывается после успеха или ошибки — перед повторным использованием результата его необходимо освободить

## Пример согласованного поведения

```text
api.log                     worker.log
1: INFO ready               1: timeout retry
2: ERROR timeout            2: INFO done
3: ERROR repeated ERROR
```

Для `patterns = ["ERROR", "timeout"]` и `Workers=2 CountOnly=false MaxMatches=2`

```text
Files[0] = {Lines: 3, MatchingLines: 2, Status: FileOK}
Files[1] = {Lines: 2, MatchingLines: 1, Status: FileOK}

Matches[0] = {FileIndex: 0, LineNumber: 2, Text: "ERROR timeout"}
Matches[1] = {FileIndex: 0, LineNumber: 3, Text: "ERROR repeated ERROR"}

Truncated = true
```

Счётчики второго файла остаются полными даже при отсутствии его совпавшего текста в результате
При `CountOnly=true` возвращаются те же счётчики файлов — `Matches` пустой и `Truncated=false`

## Критерии готовности

- Go-типы и C-типы вместе с объявлениями двух C-функций доступны для ревью
- Определены правила поиска и порядок результатов вместе с лимитами и обработкой ошибок
- Описано владение памятью
- Разработка CLI и C++ может идти независимо с опорой на общий контракт
- Заголовок подключается из C и C++ — существующие сборка и тесты проекта проходят
- Реализация поиска и вызываемая cgo-обвязка остаются отдельной работой
